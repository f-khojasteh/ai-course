# سؤالات مفهومی جلسهٔ اول

## سؤال ۱ — Constitution و حاکمیت معماری

تیم شما تصمیم گرفته تمام Business Logic در لایهٔ Domain یا Application قرار بگیرد و API فقط مسئول دریافت درخواست و ارائهٔ پاسخ باشد.

Coding Agent یک قابلیت را پیاده‌سازی کرده و همهٔ Testها موفق شده‌اند؛ اما بخشی از Business Logic مستقیماً داخل Controller یا Endpoint نوشته شده است.

- چه تفاوتی بین موفقیت Testها و رعایت اصول معماری وجود دارد؟
- قاعدهٔ جداسازی مسئولیت‌ها باید در Constitution، Plan یا Tasks ثبت شود؟ چرا؟
- چگونه می‌توان در توسعه‌های بعدی از تکرار این مشکل جلوگیری کرد؟

**پاسخ:**

۱. Passed شدن Testها نشان می‌دهد رفتارهای بررسی‌شده درست بوده‌اند، ولی لزوماً اصول معماری رعایت نشده‌اند. در این مثال، محل قرار گرفتن Business Logic با معماری توافق‌شده سازگار نیست.

۲. این قاعده باید در Constitution ثبت شود، چون یک اصل پایدار برای کل پروژه است. Plan نحوهٔ اجرای آن را مشخص می‌کند و Tasks کارهای لازم را به بخش‌های اجرایی تقسیم می‌کند.

۳. در توسعه‌های بعدی، Constitution باید مرجع Agent باشد و در Code Review هم محل Business Logic و وابستگی لایه‌ها بررسی شود. فقط به Passed شدن Testها اکتفا نمی‌کنم.

## سؤال ۲ — Specify و Clarify

مالک محصول می‌گوید:

> «کارمندان بتوانند درخواست ثبت کنند و مدیرها بعد از بررسی، درخواست‌ها را تأیید کنند.»

Coding Agent فرض می‌کند هر مدیری می‌تواند درخواست خودش را نیز تأیید کند.

- آیا Agent مجاز است این تصمیم را بدون تأیید مالک محصول نهایی کند؟
- تفاوت Assumption با تصمیم تأییدشدهٔ مالک محصول چیست؟
- حداقل دو ابهام مهم دیگر در این درخواست پیدا کنید.
- کدام ابهام‌ها باید در Specify برجسته شوند و Clarify چه نقشی در رفع آن‌ها دارد؟

**پاسخ:**

۱. خیر. اجازهٔ Self-Approval یک تصمیم محصولی و امنیتی است و باید از مالک محصول پرسیده شود.

۲. Assumption یک فرض موقت و قابل بازبینی است؛ تصمیم تأییدشده، پاسخ مشخص مالک محصول است که مبنای Specification و Acceptance Scenarios قرار می‌گیرد.

۳. دو ابهام دیگر این است که هر مدیر درخواست‌های چه کسانی را می‌تواند بررسی کند و آیا درخواست پس از تأیید قابل ویرایش است.

۴. ابهام‌های مربوط به Role، Permission و State باید در Specify مشخص شوند، چون روی رفتار سیستم اثر دارند. Clarify این ابهام‌ها را به سؤال‌های مشخص تبدیل می‌کند و پاسخ‌ها را به Specification برمی‌گرداند تا Plan بر اساس تصمیم‌های روشن ساخته شود.

## سؤال ۳ — Requirement در برابر Design Decision

در Specification آمده است:

> «هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده، بدون بررسی و تأیید معتبرِ آن محتوا، اجرا شود.»

توسعه‌دهنده پیشنهاد می‌کند یک field عددی به نام `ContentRevision` اضافه کنیم.

- کدام بخش Requirement است و کدام بخش Design Decision؟
- چرا بهتر است مکانیزم فنی در Plan/Research بررسی شود؟
- حداقل دو راهکار جایگزین برای تشخیص محتوای تأییدشده پیشنهاد کنید و Trade-off آن‌ها را توضیح دهید.

**پاسخ:**

۱. معتبر بودن تأیید برای همان محتوایی که اجرا می‌شود، Requirement است. اضافه کردن `ContentRevision` یک Design Decision برای اجرای این Requirement است.

۲. Specification باید بگوید چه رفتاری می‌خواهیم. در Plan/Research مشخص می‌کنیم چطور آن را بسازیم و گزینه‌ها را از نظر پیچیدگی و تناسب با پروژه مقایسه می‌کنیم.

۳. یک راه، ذخیرهٔ Hash محتوای تأییدشده و مقایسهٔ آن پیش از اجراست؛ فضای کمی می‌گیرد، ولی باید دقیقاً مشخص شود کدام fieldها در Hash شرکت دارند. راه دیگر، نگهداری یک Snapshot تغییرناپذیر از محتوای تأییدشده است؛ مشخص می‌کند چه محتوایی تأیید شده، ولی فضای ذخیره‌سازی و مدیریت بیشتری لازم دارد.

## سؤال ۴ — Tasks و Analyze

برای یک Feature، تعداد ۳۰ Task تولید شده و هر Requirement حداقل به یک Task مرتبط است. با این حال، یک Task به Database آماده نیاز دارد، در حالی که Migration مربوط به Database در Task بعدی تعریف شده است. همچنین دو Task دارای نشانگر `[P]` باید فایل مشترکی را تغییر دهند.

- چه مشکلاتی در Dependency و Parallelism وجود دارد؟
- انتظار دارید Analyze چه Findingهایی گزارش کند؟
- آیا پوشش ۱۰۰٪ Requirementها توسط Tasks، آمادگی قطعی برای Implement را ثابت می‌کند؟ چرا؟

**پاسخ:**

۱. ترتیب Dependency درست نیست؛ Migration باید قبل از Task وابسته به Database انجام شود. دو Task دارای `[P]` هم مستقل نیستند، چون فایل مشترک را تغییر می‌دهند و ممکن است تغییراتشان با هم تداخل داشته باشد.

۲. Analyze باید ترتیب اشتباه Dependency و علامت‌گذاری نادرست Parallelism را با اشاره به Taskهای مربوط گزارش کند. بعد، مشکل را در Tasks اصلاح می‌کنیم و Analyze را دوباره اجرا می‌کنیم؛ خود Analyze فایل‌ها را تغییر نمی‌دهد.

۳. خیر. Coverage کامل کافی نیست؛ Taskها باید ترتیب درست، پیش‌نیاز روشن و سازگاری با Spec، Plan و Constitution هم داشته باشند.

## سؤال ۵ — Implement، Validation و Converge

Coding Agent گزارش داده است:

> «تمام Taskها تکمیل شده‌اند؛ پروژه Build شده و ۱۲۰ Test همگی Passed هستند.»

اما در Code Review متوجه می‌شوید یک قاعدهٔ امنیتی رعایت نشده و یک معیار پذیرش انسانی هنوز ارزیابی نشده است.

- آیا Feature قابل اعلام به‌عنوان «کامل و پذیرفته‌شده» است؟
- تفاوت Build، Test، Validation و Acceptance چیست؟
- Converge در این وضعیت چه نقشی دارد و چه تفاوتی با Analyze دارد؟
- اگر Converge شکاف جدیدی پیدا کند، مسیر اصلاح چیست؟

**پاسخ:**

۱. خیر. قاعدهٔ امنیتی هنوز نقض شده و Human Acceptance انجام نشده است. تکمیل Implementation به معنی پذیرفته شدن Feature نیست.

۲. Build نشان می‌دهد پروژه قابل ساخت است. Test رفتارهای تعریف‌شده در آزمون‌ها را بررسی می‌کند. Validation شواهد انطباق با Specification و Success Criteria را بررسی می‌کند. Acceptance تأیید نهایی بر اساس معیارهای پذیرش است و بررسی انسانی هم می‌تواند بخشی از آن باشد.

۳. Analyze سازگاری Spec، Plan و Tasks را قبل از کدنویسی بررسی می‌کند. Converge بعد از Implement، کد موجود را با Intent مستند مقایسه می‌کند و کارهای باقی‌مانده را مشخص می‌کند؛ خودش کد را اصلاح نمی‌کند.

۴. شکاف به Task قابل ردیابی تبدیل می‌شود. سپس آن Task را با Implement انجام می‌دهیم، Build، Test و Validation را تکرار می‌کنیم و دوباره Converge می‌گیریم. معیار پذیرش انسانی هم تا زمان ارزیابی واقعی باز می‌ماند.
